Fixed
- **A block that connects again keeps the outputs it spent inside itself
  spent.** After a disconnect and reconnect of the same block across two
  spend checkpoints, outputs that block both created and spent read
  unspent, so a later re-spend was accepted where Core rejects it. A node
  that already did this keeps the wrong spends until `store/spend_durable`
  is deleted and the node restarted, which revalidates the chain
  ([116](docs/external_findings/116-reconnected-in-block-spend.md)).
- **Power loss no longer leaves the chain naming lost transactions.**
  Before it writes the confirmed tip, the connect barrier device-syncs
  every archive file the block commit names, on the configured IO backend
  so the syncs overlap. A power cut used to leave the tip pointing at bytes
  that never reached disk; the node then refused to start, rejected the
  next valid block, or wedged until the store was wiped. On open, the
  archive keeps exactly the transactions a durable record names and cuts
  the rest, which then download again. A datadir torn below a committed
  block asks for a reindex instead. A failed archive write or fsync stops
  the node instead of failing every later block, so a full disk needs a
  restart once space is freed. The store's `meta` and `store.secret`, the
  unbroadcast list, and a first mempool `meta` are written whole by
  rename; later mempool `meta` updates rewrite the 24-byte image in place
  and sync it. A torn
  address index, an interrupted `tx.head` rebuild, or a torn
  `getblockstats` cell now rebuilds itself instead of refusing or failing.
- **A full disk fails the store grow on Linux, not a later page write.**
  `fallocate` ENOSPC or EDQUOT used to fall back to a sparse file, so the
  error surfaced mid-rewrite. The grow now fails up front and leaves the
  file length and capacity unchanged, or succeeds at the smaller size the
  caller needs; only a failed rollback truncate can leave the file longer.
  Filesystems without `fallocate` (and macOS, Windows) still
  extend sparsely.
- **A killed first start no longer bricks the datadir.** A partial create
  with no chain data is replaced on the next start.
- **A block rebuilt from the store is checked against its witness
  commitment before it is served** by P2P, Esplora, or `getblock` at
  verbosity 0/2+, when its coinbase carries a commitment and a 32-byte
  reserved witness item, so damaged witness bytes on disk are refused
  instead of served. A block with neither still serves, and damage to the
  commitment magic or the reserved value is not checked; verbosity 1 and
  the paths in `docs/errata.md` are also unchecked.
- **A scripthash history read no longer drops creates committed between
  its two lists**, and does not count them twice.
- **Headers and IBD:**
  - A header at or below its parent's median time past is a permanent
    reject, as in Core; only `time-too-new` stays temporary.
  - Outbound full-relay and block-relay peers whose short `headers` batch
    ends under `--min-chain-work` (Core `-minimumchainwork`), and whose
    earlier best-known chain does not already meet it, are dropped during
    IBD (bitcoin/bitcoin#36426). Inbound and manual peers stay.
  - Below the work floor, confirm follows a matched header lead of at most
    65,536 blocks or 1 GiB, a short header batch does not extend the walk,
    and a walk faster than six headers per second since genesis is
    refused. `header.adopt` is written when the walk is proved and then
    every 2,000 headers, not on every batch.
  - A full pending-header map still accepts the next connecting header,
    evicting failed proof of work, then unconnecting headers, then lighter
    forks, then equal-work forks.
  - An unconnecting `headers` message no longer clears our outstanding
    `getheaders` (bitcoin/bitcoin#36422).
  - IBD stall detection counts solicited block bytes, and a `block`
    message under 80 bytes counts against the peer's rate window.
  - Tip-follow no longer drops a fast peer for serving the blocks it was
    asked for.
- **P2P:**
  - A later ping's pong no longer overtakes the reply to an earlier
    message, a peer gets one pong per ping burst, and that pong is charged
    at its fixed 64-byte estimate on the per-peer send budget;
    compact-filter and `cmpctblock` replies are charged their payload
    size.
  - A compact block is relayed only after its body matches the witness
    commitment, and near the tip a block is also asked of other
    high-bandwidth peers. A `blocktxn` that cannot fill, or fails for a
    reason other than a consensus verdict, asks the announcing peer for
    the full block again.
  - `getblocks` is answered as Core answers it (`MSG_BLOCK`, stop before
    `hashStop`, continue a full page), so bitcoinj syncs from the v1
    listener.
  - The orphanage is keyed by wtxid, a re-parked orphan is not evicted
    first, and a just-rejected transaction is not requested again from
    another announcer.
  - A loopback peer that arrived through Tor or I2P no longer takes a
    `127.0.0.1` net permission.
  - A burst of unsolicited small blocks (e.g. 108 unsolicited bodies in
    the versionbits test, whose period is 144) no longer trips the
    decode-queue cap.
  - An inv of a tip that is not a descendant of the last tip offered is
    held 200 ms and sent once, the same as a reorg header announcement; a
    normal extend goes out immediately.
  - Idle listeners no longer exhaust file descriptors: health, Esplora,
    and unfinished BIP324 handshakes are capped and timed out, and
    descriptors are reserved for the store and RPC.
- **Tor, I2P, and proxy:**
  - Onion services and I2P sessions come back after tor or i2pd
    restarts, with saved keys and a 1 s / 1.5x backoff capped at 10
    minutes (Core's growth factor; the cap is ours); the node stops
    announcing the address while it is down.
  - `--tor-control` gives up after 20 s per step and bounds reply size,
    and SIGTERM during the Tor step exits at once.
  - A Tor control reply with a multi-byte character no longer panics,
    and a status code that is not three digits is an error.
  - `--proxy` uses the same DNS seed rules as a direct start (none with
    `--connect`, on a custom signet, or on regtest).
- **Mempool and mining:**
  - A restart after a reorg no longer reloads a child whose parent is
    gone, which made every template invalid.
  - `getblocktemplate` and `generate*` fail as Core does when the next
    block's earliest time is past the two-hour future limit.
  - Overlapping regtest `generate` calls no longer mine one transaction
    twice.
  - A multi-transaction `testmempoolaccept` leaves the mempool as it was.
  - `maxburnamount` checks each output, as in Core; the
    `sendrawtransaction` reject is now `-25`.
  - Unconfirmed admission keeps legacy scriptCode constant and charges
    each legacy sighash preimage against 32,000,000 bytes per
    transaction, so a standard multisig spend of any size fits. Block
    connect is unchanged.
- **RPC and CLI:**
  - `gettxout`, `waitforblockheight`, `gettxspendingprevout`,
    `getblockhash`, and `getblock`/`getrawtransaction` verbosity read their
    numbers as Core's `int`: out of range is `-1`, not a wrap to 0.
  - A refused request (401, 404, 405) gets its answer instead of a
    connection reset.
  - A non-object batch element gets Core's `-32600` reply.
  - Side-branch `getblock` verbosity 1 reports `size`, `strippedsize`,
    and `weight`; `getmempoolinfo.maxdatacarriersize` is `100000`, not
    `null`.
  - `getblockfilter` on a block that never connected answers Core's `-5`.
  - `disconnectnode` on a peer already leaving returns `-29`.
  - rbitcoin-cli accepts negative numbers and types each method's
    parameters, so a digit-only hex string stays a string.
  - `--help` and `--version` print to stdout, and help states the real
    per-peer download cap (64).
  - The startup line's `io=` names the backend in use.
- **Electrum and Esplora:**
  - Electrum outpoint subscribers hear a mempool spend at once.
  - Electrum `mempool.get_fee_histogram` answers in sat/vB with each
    bin's own size.
  - Electrum answers malformed JSON with `-32700` and keeps the
    connection, and its port is released when the node stops.
  - Esplora answers 404 on the transaction body, hex, raw, and outspend
    routes for a stored transaction that is neither confirmed nor in the
    mempool; `/tx/:txid/status` answers `200 {"confirmed":false}` for a
    txid that was never stored, and a reorg gets 503 `chain view moved`.
  - An outspend lookup past a transaction's outputs answers unspent
    instead of 500.
  - Bulk outspends requests are capped at 250,000 outputs, so a 3 KB URL
    can no longer exhaust memory.
  - `POST /txs/test` rounds vsize up, and merkleblock proofs use the
    stored header.
- **`--sp-tweaks-dust 545`, not 546, matches Cake's electrs.** Behavior is
  unchanged; only the help and docs were wrong.
- **A block body parked below `--min-chain-work` (Core `-minimumchainwork`) is fetched again after its
  peer leaves.** Tip follow parks a requested body while its chain is still
  under the floor. The body stayed asked after that session ended, after it
  was evicted from the parked set, or when it was too large to park, so no
  other peer was asked for it until 4096 other asks had gone out. Each body
  ask is now held by the session table, the parked body, or the accept in
  progress, and is released when that holder lets go.
- **Tip-follow reads a `block` message with bytes after its last
  transaction,** as Core does. The message was dropped as unknown, so a
  peer that sent one never delivered that block. `submitblock` and the IBD
  body path already ignored those bytes (#1773).
- **Electrum `blockchain.transaction.broadcast`, Esplora `POST /tx` and
  BlindBit `forward-tx` answer the txid for a transaction already in the
  mempool,** as `sendrawtransaction` does and as electrs and Esplora in
  front of Core do. They returned `duplicate <txid>`, so a protocol where
  both parties broadcast the same transaction (Bisq MuSig) aborted (#1701).
- **A broadcast no longer returns the txid of a transaction that a
  concurrent package then removes.** `sendrawtransaction`, Electrum
  `blockchain.transaction.broadcast`, Esplora `POST /tx` and BlindBit
  `forward-tx` could answer success for a transaction that a
  `submitpackage` or a 1p1c pair had just put in the pool and then took
  back, so the caller held a txid that was never relayed. A broadcast that
  meets such a transaction (or a spender of one) now waits until that
  admit is done, as Core does under `cs_main`, then answers from the pool
  or admits the transaction itself (#1856).
- **A torn Class A page no longer drops creates the tip already names.** Open keeps exactly the creates a durable `header_txs` range or `class_a.synced` names, and a still-zero `input.body`, `txstat.*`, `seqsigwit.body`, or `spent.body` tail is kept as data, because a coinbase edge, an unstamped txstat cell, an empty seqsigwit pad, and an unspent slot are zero bytes. On Windows a recycled `HANDLE` is bound to the completion port again; the old "already associated" hit left a read with no completion and the connect flush aborted.
- **A compact block whose reconstruct fails its witness commitment is asked
  for again as a full block from the same peer.** Only other high-bandwidth
  peers were asked, so a single `--connect` or noban peer left the node one
  block behind until another header or a child arrived. Core's `FillBlock`
  asks the same peer and does not score it, because a short-id collision is
  not the sender's fault. The peer is no longer scored (#1791).
- **Docs match the code for 0.10.0.** An audit before the release corrected
  stale names and numbers across the operator, schema, interface, test, and
  process docs: `tip: accept` JSON keys, the `run/*.addr` list, RPC default
  ports, refusal lines removed with flat `*.idx.meta`, the tx-head lookup
  order, renamed tests and functions, and the BIP54 rows in the BLVM
  crosswalk. `docs/esplora-openapi.yaml` gains the four output-by-position
  routes.
- **Docs name the current release and schema.** `README.md`, `SECURITY.md`,
  and the mainnet runbook said the published release was 0.9.0 and named
  schema 27 or 29 as the one an upgrade writes. They now follow the in-tree
  version and point at the schema table in `docs/operator/storage.md`
  instead of repeating it.
- **An IPv4 peer accepted on a `[::]` listener is an IPv4 peer.** Linux
  makes that listener dual-stack, and the peer was kept as
  `::ffff:a.b.c.d`. `getpeerinfo.addr` showed the mapped form, a local
  `127.0.0.1` client that misbehaved was discouraged (loopback is exempt)
  and refused on reconnect, and a discouraged remote IPv4 address did not
  match the same address seen elsewhere. The listener still accepts IPv4,
  as before.
- **`--net-permission` reads `::ffff:a.b.c.d` as IPv4 `a.b.c.d`, as Core
  does.** A grant written in the mapped form `getpeerinfo` used to show
  (`noban@::ffff:127.0.0.1`) still matches that peer, now that it is kept
  as IPv4. The prefix counts IPv4 bits, so `::ffff:10.0.0.0/8` is
  `10.0.0.0/8`, and a prefix over 32 such as `::ffff:0:0/96` is rejected
  at startup with "Invalid netmask".
- **Electrum keeps a request that arrives in pieces.** A request line
  split across TCP reads lost its first part when a push (a scripthash
  tick, a new tip, a mempool announce, a silent-payment scan step, or a
  tweaks wave) ran between the pieces, and the client got
  `-32700 parse error` instead of its reply. The bytes read so far now
  stay with the connection until the line ends. The request-line cap and
  its `-32600 request line too long` answer are unchanged (#1806).
- **Electrum `blockchain.silentpayments.unsubscribe` no longer waits on
  the scripthash index.** With `--sh-index` off it answered `scripthash
  index disabled`, and while the index rebuilt or froze it answered
  `scripthash index rebuilding` / `updating`, although the subscribe it
  ends was served: a silent-payment scan reads the tweak index, not the
  scripthash index.
- Electrum `blockchain.transaction.get` now returns Bitcoin Core's standard missing-transaction error text (`RAW_TX_NOT_FOUND`) instead of `tx not found` when a txid is absent from both chain and mempool.
- **Esplora `/scripthash/:hash` takes `sha256(scriptPubKey)` hex in digest
  order, as electrs does.** The path and the `POST /scripthashes/txs` entries
  were read byte-reversed (Electrum's scripthash order), so a client sending
  the electrs, blockstream.info, or mempool.space form got 200 with an empty
  history. This covers `/scripthash/:hash`, `/utxo`, `/txs`, `/txs/chain`,
  `/txs/mempool`, `/txs/summary`, the POST routes, and unix-socket
  `/internal/scripthash/:hash` and `/internal/scripthash/:hash/history`. A
  client that sent the reversed form now gets empty results: send the digest
  unreversed, or use `/address/:address`.
  Electrum is unchanged (#1662).
- **Esplora `/tx/:txid/status` answers `200 {"confirmed":false}` for a txid
  that is neither stored nor in the mempool, as electrs, blockstream.info and
  mempool.space do.** It
  answered 404, which `esplora-client`'s `get_tx_status` returns as an error,
  so a client asking before it broadcasts (rgb-lib's refresh after an RGB ACK)
  failed. `/tx/:txid`, `/hex`, `/raw` and the outspend routes stay 404 for that
  txid, and so does `/status?asof=`. A stored transaction that was reorged out
  and is not in the mempool answers the same `200 {"confirmed":false}`, as
  electrs does (#1916, #2092).
- Peers on a dedicated `=onion` listener no longer trigger IP discouragement or eviction cooldowns for other peers sharing a non-loopback Tor forwarder.
- **Nightly fuzz builds again.** `drain_pending_now` takes a `PeerOutTx`,
  so the block and compact drain harnesses build their writer channel with
  `peer_out_channel()`.
- **`getblockfilter` walks at most 10,000 stale blocks.** A stale block
  is rebuilt from its best-chain fork point. That walk had no depth bound,
  so a request for the tip of a long stored side branch rebuilt every block
  on it. Past 10,000 stale blocks, the same bound as Esplora's stored-header
  walk, the request now fails with "Filter not found. Stale branch is
  deeper than 10000 blocks." before any body is rebuilt. Core keeps every
  connected block's filter and has no such limit (#1684).
- **A block that connects during a getheaders reply is still announced.**
  An empty headers reply marked our current tip as sent to the peer. A
  block that connected while the reply was built became that tip, so its
  announcement was skipped and the peer waited up to two minutes for the
  headers poll. The reply now marks the block where the peer's locator met
  our chain.
- **`getpeerinfo.bytessent_per_msg` counts what was sent.** It was always
  `{}`: nothing wrote the per-message map. The session writer now counts
  each message it puts on the wire, so a v1 peer gets payload plus the
  24-byte header, the same rule `bytesrecv_per_msg` uses, and a v2 peer
  gets its BIP324 contents plus 20 bytes (see the v2 counter below). That
  includes `sendheaders`,
  `sendcmpct`, the first `ping` and `feefilter` at session start. The
  version handshake (`version`, `verack`, `wtxidrelay`, `sendaddrv2`) is
  not counted.
- **A panicked `tx.head` insert keeps the batch.** `ibd-confirm-head` leaves that batch parked until the insert returns `Ok`. The write puts it back on the pending list when the worker panics.
- **The header walk drops only its oldest dead end at the cap.** Past 1,024
  look-ahead tips that every peer left empty, the walk cleared the whole
  set, so one more mark forgot every earlier one. It now drops only the
  oldest, as the refused-tip set already does.
- **An empty headers reply no longer stalls the header walk until restart.**
  Before the work floor, an empty reply counted toward abandoning the walk
  tip even when we had not asked that peer. Once every taller peer had sent
  one, the walk could mark its own starting point dead, drop every later
  batch built on it, and stall until the node restarted. A reply now counts
  only while the walk is still at the tip its ask named, and the starting
  point is never marked dead.
- **An empty headers reply below the work floor no longer re-asks the peer
  that just answered empty.** The reservation now moves to another peer that
  has not answered empty at the walk tip, preferring one taller than the tip.
  The all-peers-empty rewind therefore hears from every taller peer still on
  the walk instead of waiting for the reserved peer to time out.
- **IBD `headers` and `notfound` frames take the peer's session window.**
  Both are charged to the same messages and bytes budget as any other P2P
  frame before their decode is spawned, so a peer that floods either one is
  disconnected. The one `headers` reply that answers each outstanding
  `getheaders` stays exempt, so header sync is not clipped.
- **IBD asks for an equal-work sibling block and stops re-getting a body that
  only arrives mutated.** A `--connect` or noban peer that answered a block
  getdata with a mutated copy re-opened that hash on every copy, so `ordered`
  never emptied and IBD never left catch-up; the sibling block, whose header
  breaks no rule, was never asked for. The sibling is now recorded and asked
  for once the occupying header is abandoned (Core asks at once, on
  `nChainWork >=`), and after three copies from a peer IBD keeps, the header
  is taken off the path instead of re-opened (#1811).
- **IBD keeps a `--connect` peer that sends a mutated block.** It used to
  disconnect it and dial it again, and with one peer that kept serving the
  block the node never settled. Core never disconnects a manual peer for
  misbehavior; tip-follow already kept one, and IBD already kept a stalling
  one (#1265). The block is still asked for again (#1772).
- **An IBD `notfound` is no longer block progress.** A peer that still owes a requested block now stalls out even while it keeps sending `notfound`. A `notfound` counts only for blocks the peer was asked for, and keeps the peer off each for 30 s unless it announces that block: padding the message or announcing other blocks no longer hands the block straight back. When the per-peer record is full, the block stays owed. The record expires its oldest answers in O(1) instead of scanning the whole map for every hash.
- **A rewind no longer disconnects a confirmed chain that grew during its
  search.** The rewind read the confirmed tip after selecting a heavier
  fork. If confirm extended the chain while the walk ran, that extension
  became the tip the depth check measured, and the rewind disconnected it
  even though the fork was now the lighter chain. Both the off-lock pass and
  the pass under the coordinator lock now read the tip before selection,
  compare it again under the tip commit before disconnecting, and hold that
  commit through the commit. A path that no longer disconnects is left for
  confirm, and a moved tip selects again on a later turn (#1736).
- **IBD selects a heavier fork as deep as the rewind cap allows.** Below
  the work floor a header rewind may disconnect 65,536 blocks, but the walk
  that finds the fork's connected ancestor stopped at 10,000 headers. A
  heavier fork that needed a longer walk was never selected, and the node
  stayed on the lighter chain. The coordinator's and the header thread's
  heavier-fork checks now walk as far as the rewind cap in force needs
  (65,537 headers below the floor; 10,000 above it, as before), pass over
  a fork deeper than that cap, and rewind to the candidate with the most
  work rather than the first heavier one. Checks that run under the
  coordinator lock, on a reject or a held side block, still walk 10,000
  headers. Below the floor they leave the choice to the next coordinator
  check when more than one candidate is in play, and they hand over what
  they miss and any fork whose rewind could not run yet. An unplanted
  header-walk tip 65,537 or more above the confirmed tip is not walked
  (#1691).
- **Refused listener sockets log at most once a second.** The health
  listener wrote one warning per refused connection past its cap, and every
  listener (P2P, Electrum, Esplora, health) wrote one per socket it refused
  to keep descriptors for the store, so a client that reconnected in a loop
  could fill the log. Those lines now share the per-thread limit the RPC
  max-connections line already has.
- **A full mempool no longer grows `mempool/tx.body` on every admission.**
  Each admit reused the slot its eviction freed but appended the new payload,
  leaving the dead payload in the body. Compaction only ran on block connect
  and only when dead slots were a large share of the table, so a pool that
  stayed near full kept every admitted payload and open read the whole body.
  An admit now compacts first when dead payloads reach the live payload bytes
  (#1674).
- **A full mempool evicts with one disk sync per pass.** Making room for a
  new transaction used to sync the mempool files once for every chunk it
  dropped, holding up other admits each time. The pass now syncs once,
  after its last chunk and before it returns, so an evicted transaction
  still does not come back after a crash.
- **A failed mempool compaction no longer revives a removed transaction.**
  Compact swapped in the packed body and slot table before the temporary-file
  writes could fail, so the graph kept the old slot numbers while the store
  used the packed ones. A later removal then marked the wrong slot, and the
  next successful compact reloaded the removed transaction from its still-LIVE
  slot. The images are now installed before the store adopts them, so a failed
  write leaves body, slots, and the live counts as they were. If the body
  rename lands and the slots rename fails, the pool follows the packed body
  and keeps writing the live table to `slots.tmp` until a later persist or the
  next open links it, so removals made in that window survive the restart.
- **Tip-follow asks a `--connect` or noban peer again for a block it sent
  as a mutated copy.** The copy was dropped and the request forgotten, and
  nothing asked for the block again until a later message from that peer,
  so a single `--connect` peer could leave the node one block behind. Core
  asks again at once. A copy whose witness bytes the block does not commit
  to is handled as mutated, as Core's `IsBlockMutated` does: the sender is
  punished like the other mutations, and the block is not marked invalid.
  A signet block with no witness commitment is a consensus failure (Core
  `CheckSignetBlockSolution`, `bad-signet-blksig`): the hash is marked
  invalid and is not asked for again. A signet body that still carries
  witness data and has no commitment stays a mutated copy, because Core
  reports `unexpected-witness` first (#1771).
- **A frame parked for the peer's send budget no longer hides a stalled
  writer from the ping timeout.** A decoded non-block frame is put back at
  the front of the decode queue while the writer is over budget. The
  heartbeat treated every non-empty queue as a frame still waiting on a
  decode permit, so the ping and block-download timeouts stayed suspended
  and the peer kept its slot until something else dropped it. A held frame
  now leaves those timeouts armed. A frame still waiting to decode at the
  front still suspends them, and request expiry stays suspended while any
  frame is queued, including one behind a held front.
- **A locator with the zero hash, or with no known hash, no longer serves
  genesis.** `headers_after_locator` treated the zero hash as "start at
  genesis" and broke out of the locator walk, so a valid hash later in the
  same locator was ignored. A locator that matched nothing also started at
  height 0. Both now skip unknown hashes, use genesis as the fallback fork
  point, and reply from the block after it. A known hash on a stale branch
  that contains our tip is still not mapped to that tip; the walk skips it
  and keeps looking for an active-chain entry, falling back to genesis only
  when none matches. The header-cache fallback starts after genesis the
  same way, at `chain[0]` when its window no longer includes genesis.
- **NixOS module fixes.** `sv2.tp.authoritySecretFile` is loaded as a
  systemd credential, so a root-only path such as `/run/keys/...` works
  (the unit used to restart forever). `silentPaymentIndex` with
  `pruneSeqSigWit` is allowed, as the node has allowed it since 0.9.1. A
  `$` in `alertNotify`, `startupNotify`, or `extraArgs` reaches the node
  instead of being expanded by systemd. `rpc.rest` works with only the
  unix socket. A `v1` `netPermissionBind` on the P2P, Electrum, or Esplora
  port, or with `p2p.maxInbound = 0`, fails evaluation instead of startup.
- **An IBD peer's ping that lands while its pong is written is answered.**
  The IBD pong slot used release/acquire ordering, so the reader and the
  writer could each miss the other's store and the ping was never answered.
  The tip-follow session had the same race fixed earlier. Both now share one
  pong type.
- Evicting a peer on a marked onion listener no longer pauses new connections through the same loopback forwarder.
- **Forwarded Tor peers can use the shared inbound limit.** A P2P listener marked `=onion` uses the node's inbound connection limit and handshake timeout for all forwarded peers. Ordinary TCP listeners still cap unfinished handshakes per source IP.
- **The overlay cjdns mesh survives a `cjdroute` crash.** `cjdns-run.sh`
  restarts the angel and its core as a pair after the runner's cjdns 22.3
  segfaults around the first TCP, so a journey is never handed a dead TUN.
  The restarted pair reclaims the same address, and the runner fails with
  the cjdns log when the device cannot come back.
- **The overlay cjdns supervisor no longer exits with the TUN down.** The
  angel can die alone and leave its core behind. The supervisor used to call
  that survivor healthy and exit; the core then exited 232 at the 20-second
  `Security_setupComplete` deadline, the TUN went with it, and nothing
  restarted the pair. It now kills the orphan core, clears the device and
  starts a fresh pair on the same address. `run.sh` also waits for both
  cjdns addresses to bind before each journey, so a dead TUN fails the
  harness with the daemon logs instead of panicking in a journey that means
  to bind it.
- **Missed mutants through nightly run 44483845560.** Pins and equivalent rewrites cover every `missed.txt` line after the merged kill at run 43385435784.
- **Pruned RPC answers match Core's codes.** `getblock` at verbosity 0 or
  2+ below `pruneheight` returns `-1`; verbosity 1 still answers with the
  txids. An unstamped `getblockstats` below `pruneheight` returns `-1`; a
  stamped block still answers. A blockhash-scoped `getrawtransaction` below
  `pruneheight` returns `-1`; an unscoped one returns `-5` with Core's
  no-txindex text. LND can restart after more than 288 blocks offline on a
  pruned backend.
- **Regtest's difficulty period is 144 blocks, as in Core.** Its target
  timespan was rust-bitcoin's two weeks, so the period was 2016 blocks.
  The minimum-difficulty walk now stops at a multiple of 144.
  `getnetworkhashps` with `nblocks` at or below 0 counts back to the last
  multiple of 144. `getblocktemplate` sets `mintime` from the new period:
  the timewarp floor applies at a multiple of 144, and the floor that keeps
  a period's last block from being earlier than its first applies one height
  before it. With `--regtest-pow-bits`, a block at a multiple of 144 now
  keeps its parent's bits. Two kinds of block mined there before this change
  no longer pass: one with the `--regtest-pow-bits` bits whose parent has
  the pow limit, and one with the pow limit, more than two spacings after a
  harder parent. A datadir holding such a block still opens, because open
  does not check `nBits` again, but a node syncing that chain rejects the
  block, so the chain needs to be mined again. A chain whose blocks all have
  the pow limit is unaffected (#1775).
- **The GitHub Release thanks contributors again.** `release-notes.sh`
  started its range at the newest tag, which in `release.yml` is the tag
  being released, so the automatic thanks line was empty (0.9.0's Release
  has been corrected by hand). It now starts at the newest release tag the
  commit descends from, and the Release job fetches full history. The
  release playbook also runs `release.yml` on the ship branch before
  merge, so a Windows, Darwin, image, or NixOS VM failure shows before the
  tag is pushed.
- Remove the test wave from the shared script pool after the republish test finishes, so later tests cannot mistake it for their own wave.
- **Every outbound message kind takes its own size on the send budget.**
  `getheaders`, `getblocktxn`, and `version` were charged a flat 64 bytes
  whatever their length. The size table now lists every message kind, so
  a kind it does not list fails the build.
- **The 4 MiB per-peer send budget counts every queued message.** Block
  announces (`headers`, `inv`, `cmpctblock`), `getheaders`, pings,
  `getaddr`, `feefilter`, `sendcmpct`, and our own `addr` announce were
  queued without a charge, yet the writer still subtracted their size, so
  a session read new requests while replies past the budget were still
  queued. Every message is now charged when it is queued and released
  once it is written, as Core's `nSendSize` does. A peer that stops
  reading now pauses at the budget, counting those messages too.
- **A scripthash index fault no longer wedges the chain.** A `Corrupt` or I/O error from the SH index during a disconnect, from a write-behind append, or from a history, listunspent or count read of a torn key used to fail the block or every read of that key (`scripthash extent last page not ver=2`) and leave the node unable to disconnect or connect, with `RBITCOIN_SH_FORCE_REBUILD` unreachable below tip. The index is now marked degraded: blocks keep connecting and disconnecting with SH deferred, Electrum returns `scripthash index rebuilding` as a JSON-RPC error and Esplora answers 503 with the same text, and a background supervisor waits for in-flight reads, wipes the index, rebuilds it from Class A, and re-arms write-behind. A read that overlaps the fault, the rebuild, or a disconnect's unlink batch is refused instead of returning a partial answer (503 on Esplora, the same JSON-RPC error on Electrum). A `store/scripthash.degraded` marker, published with a synced rename and directory fsync, makes a restart wipe the broken index at open; it is removed only after the replacement head's `SEAL` and `include_hwm` are durable. `RBITCOIN_SH_FORCE_REBUILD` now also wipes at open, not only at tip entry. `RBITCOIN_SH_AUTO_REBUILD=0` (a new flag, default on) leaves the index degraded until a restart. A write-behind error that is not a scripthash `Corrupt` or I/O error still halts as before. No schema change. The wipe also clears the ingest and sealed overflow heads, which a cold rebuild used to leave in place. Tip entry and the in-place rebuild take one owner lock for the SH build, so they never write the run and unsorted files together; a degraded index at tip entry is left to the supervisor. The wipe disarms an unlink undo record left armed by a failed unlink. An Esplora request the timeout layer drops keeps its read guard until its blocking read returns. `blockchain.scripthash.unsubscribe` works while the index rebuilds, and a refused Electrum read drops the join it filled. `scripthash index rebuilding` and `scripthash index updating` are documented in COMPAT.md and the OpenAPI `Unavailable` response.
- **A zero scripthash occupancy sidecar does not wipe a live head.**
  A kill between the slot-table write and the sidecar rename used to
  leave `.occ` at 0. Open treated that large head as empty, so the next
  insert bulk-filled over the live slots and a packed shard skipped the
  ingest soft-clear. Open scans that head and keeps the count it finds.
  An empty large ingest is removed instead, and the file is created on the
  first insert rather than when the store is created.
- **Core's `wallet_txn_clone.py` passes again.** The functional test
  wallet left an Esplora 404 response open. Python 3.14 then printed a
  finalizer error to the wallet's stderr, and Core's harness fails any
  node that writes to stderr. Esplora answers 404 for a conflicted
  transaction since this release.
- **Silent-payment labels are read as BIP-352 `u32` values and capped as
  they are read.** `blockchain.silentpayments.subscribe` folded a label of
  2^32 or more into a smaller one (2^32 became label 0), and it
  deduplicated the whole label list before refusing more than ten, so one
  long list cost quadratic CPU. A label past `u32` is now refused, and the
  eleventh distinct label stops the read.
- **The leftover tweak-file notice names the real flag.** Opening a store
  that still had pre-schema-17 `sp_tweaks.idx` / `sp_tweaks.body` files
  printed "--sptweaks backfill regenerates", a flag the node refuses. It now
  says `--sp-tweaks`, and the three leftover-file notices on open are WARN
  log lines instead of bare stderr.
- **The strong-bit image no longer stops the node at 2^31 creates.** `strong_tx`
  is one bit per create and was sized by the 256 MiB Class C load cap, which
  holds exactly 2^31 bits. The create past that index asked for a page beyond
  the reservation and failed with `strong bit image exceeds the reservation` on
  every retry, so the node could not confirm the block that carried it. The
  image now reserves address space for 2^33 creates from a constant of its own;
  the Class C load cap keeps its original job for `confirmed` and
  `header_txs_*`. Only address space is reserved, so resident memory stays one
  bit per create and operators see no change at today's chain height.
- **`submitpackage` names Core's package reason in `package_msg`.** When
  the package evaluation refuses a 0-fee parent because its child leaves
  the ephemeral anchor unspent, `package_msg` is `unspent-dust`; when the
  package would exceed the cluster limit, it is `too-large-cluster`. Both
  were `transaction failed`. The per-member errors are unchanged. Checks
  run in a different order than Core's, so a package that fails several
  rules, or a script, may name a different reason.
- **Three races in shared counters and flags:**
  - Two peers' heartbeats could both time out a noban peer's headers sync
    and both release the one sync slot. The count wrapped, so no headers
    sync could start again until restart while the header tip was more
    than a day old. A late heartbeat could also end the sync the peer had
    just restarted, so a second getheaders went out.
  - The IBD confirm queues counted a batch after handing it over, so the
    next stage could count it out first and leave a batch that was never
    there. Lookup's room for new work shrank by one each time.
  - A mempool change during a fee or transaction snapshot refresh could be
    lost, and that snapshot stayed stale until it aged out.
- **The Class A tear-guard copy no longer locks the append.** One thread appends each stem and publishes that length after the pwrite. The tip flush reads only up to the length it loaded, writes the inactive tail slot, and fsyncs that slot in the same sync as the stems. The next body write no longer waits out that copy, so the confirm write queue is not stuck behind it. A page-0 image stores that loaded length before its checksum. Open writes the tail slot's length into that same page once, including when the page already holds the image without that length, so a length torn in during the copy does not hide a zeroed tail.
- **A replay of a known-invalid body costs no lane slot.** `on_block` drops it
  after the header checks, before relay and enqueue. A bad-proof-of-work
  header still scores the peer.
- **A rejected tip block no longer runs index work.** The tip path publishes
  the index wave only after the script wave passes.
- **`getblockcount` does not stall on a tip-pair script race.**
- **A crash just after a `tx.head` roll no longer fails the next start.**
  When the open cut dropped the new tail, the segment whose seal was still
  running became the tail without a table, and open failed with
  `tx.head insert: open missing OA`. Open now rebuilds that segment from
  the archive.
- **A peer that did not send `wtxidrelay` hears of a transaction as
  `MSG_TX` by txid.** Every peer was sent `MSG_WTX` by wtxid, which BIP339
  allows only after `wtxidrelay`. A pre-70016 client such as bitcoinj could
  not parse the inventory type and dropped the connection on every relayed
  transaction. The per-peer announced set now holds the hash the peer was
  sent, as Core's known-inventory filter does (#1700).
- **`getdata` `MSG_TX` is answered without the witness,** as Core does.
  Only `MSG_WITNESS_TX` and `MSG_WTX` carry it, so a client that asks by
  `MSG_TX` gets a transaction it can parse (#1700).
- **A peer that sends `wtxidrelay` after `verack` is disconnected,** as
  Core does. The relay mode is fixed when the handshake ends, so a tx INV is
  never matched against the other hash (#1700).
- **A `wtxidrelay` from a peer below protocol 70016 is ignored,** as Core
  does. We send our own only from that version up, so such a peer still
  hears of a transaction by txid (#1700).
- **A transaction announced by txid that confirms in the tip block before
  the peer's `getdata` is still served,** from that block, as one announced
  by wtxid already was. `MSG_TX` gets it without the witness,
  `MSG_WITNESS_TX` with it (#1700).
- **`getpeerinfo` counts a v2 message as Core does.** `bytesrecv_per_msg` and
  `bytessent_per_msg` added the 24-byte v1 header to the payload for every
  peer, so a message with a short id read 3 bytes high and one in the long
  form (`sendheaders`, `verack`, `version`) read 9 bytes low. A v2 message is
  now its BIP324 contents plus the 20-byte cipher expansion, and the sums
  follow. A v1 peer keeps payload plus 24.
